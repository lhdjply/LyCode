# LyCode 功能

首次使用与各项能力。构建、运行与测试命令见 [README](../README.md)。

---

## 首次使用

1. 启动后用左侧的**工作区**行选择项目目录。
2. 打开 **设置 → Provider**，新增一个 Provider：
   - **Anthropic Messages**：Base URL 填 `https://api.anthropic.com`，API Key 填 `sk-ant-...`
   - **OpenAI 兼容**：Base URL 填 `https://api.openai.com/v1`（或自建网关地址），API Key 按需
   - **模型列表**每行填一个模型 id，例如 `claude-sonnet-4-20250514`
3. 在输入框下方那一行选择**模式**（左下）、**模型**与**思考等级**（发送按钮左侧）。
4. 在底部输入框描述任务，`Enter` 发送，`Shift+Enter` 换行。

会话模式的含义：

| 模式 | 行为 |
| --- | --- |
| `plan` | 只读。带副作用的工具会被**直接拒绝**（不弹窗），产出计划供审阅 |
| `build` | 默认。读写文件与执行命令都需要确认 |
| `edit` | 文件写入自动放行，执行命令仍需确认 |
| `yolo` | 全部放行。请自行判断风险 |

## 平台差异：shell

`Bash` 工具名与权限能力名（`bash`）在两端保持一致，但**执行的 shell 按平台不同**，而且给模型的工具说明会如实声明实际用的是哪一个：

| 平台 | shell | 启动方式 |
| --- | --- | --- |
| Linux / macOS | `/bin/bash`，不存在则 `/bin/sh` | `-lc`（`-l` 让登录 shell 的 PATH 生效，否则从 Dock/Finder 启动时 `node`、`cargo` 会"找不到命令"） |
| Windows | `pwsh.exe`（PowerShell 7）优先 → `powershell.exe` → `cmd.exe` 兜底 | `-NoProfile -NonInteractive`；cmd 用 `/d /s /c` |

Windows 上**刻意不用 bash**：原生环境没有 POSIX shell，硬塞一个就会让模型写出解析不了的命令。这是踩过的坑——工具说明曾写死"命令通过 `bash -lc` 执行"，而执行走的是 `cmd.exe`，于是模型写的 `for c in gcc; do command -v $c; done` 在 cmd 下必然失败，而且 cmd 的报错走 stderr，最后只剩一句光秃秃的"命令以退出码 1 结束"。契约必须随执行方式走。

Windows 上还做了三件必须的事：

| 事项 | 原因 |
| --- | --- |
| `-EncodedCommand`（UTF-16LE + Base64）传命令 | 命令里的引号、`$`、中文、换行要经过 QProcess → CreateProcess → PowerShell 三层转义，任何一层出错都是静默变形；编码后只剩 `[A-Za-z0-9+/=]` |
| 前缀强制 UTF-8 输出 | 否则中文 Windows 上按控制台代码页（936）输出，而调用方按 UTF-8 解码，中文变乱码 |
| 注入 `sleep` 垫片 | PowerShell 的 `Start-Sleep 2` 按**毫秒**解释位置参数（2ms 而不是 2 秒），而 `sleep 2` 恰恰是最常见的等待写法。没有垫片，命令会"成功"但等待时间差三个数量级——比直接报错更危险 |

环境变量 `LYCODE_SHELL` 可以显式指定，例如 `LYCODE_SHELL=pwsh.exe`。

`src/tools/ToolUtils.h` 的 `ShellSpec` 是这一层的唯一事实来源：`metadata()`（拼给模型的说明）和 `execute()`（真正启动进程）必须拿到同一个结果，且探测结果进程内缓存一次——两次探测结果分叉正是上面那个故障的本质。

## 后台任务

`Bash(run_in_background: true)` 让命令在工具返回之后继续跑（起 dev server、跑耗时测试）。这带来三个必须解决的问题，也正是这一节的全部内容：

| 问题 | 处理方式 |
| --- | --- |
| **生命周期** | 工具调用早已返回，栈上的 `QProcess` 承载不了它。`BackgroundTaskRegistry` 接管所有权，并在会话关闭 / 运行时就绪销毁时 `stopAll()`，不留孤儿进程 |
| **输出去哪** | 边读边落盘到 `<数据目录>/tasks/<task_id>.log`，内存只保留 **8 KiB 尾部预览**。后台任务可能产出几十 MB，全留在内存里会撑爆 |
| **完成通知** | 任务在 turn 之外异步结束，模型不会自己知道。注册表在结束时生成一条 `<task-notification>`，由运行时注入下一轮上下文 |

配套的两个工具（别名按既定语义）：

| 工具 | 别名 | 作用 |
| --- | --- | --- |
| `TaskOutput` | `BashOutput` / `AgentOutput` | 读任务状态与输出；`block=true`（默认）会等到任务结束，`timeout` 上限 600s |
| `TaskStop` | `KillBash` / `KillShell` | 终止任务，或查询一个已结束任务的状态 |

通知的投递时机语义一致：**每次模型步开始前**投递。任务结束时如果正在跑 turn，模型在下一步就看到；如果当时空闲，则在下一次输入的首次模型步看到。通知是一条 `modelOnly` 消息，UI 不会把它显示成用户说过的话。

通知的形状`<task-notification>` 同形，便于模型稳定解析：

```xml
<task-notification>
<task-id>task_xxx</task-id>
<task-type>bash</task-type>
<status>completed</status>
<exit-code>0</exit-code>
<output-path>/home/u/.cache/lycode/tasks/task_xxx.log</output-path>
<bytes>1234</bytes>
<duration-ms>2013</duration-ms>
<output-tail>…输出尾部…</output-tail>
</task-notification>
```

界面：状态栏用警示色常驻显示 `· 后台任务 N`。这条提示**必须是 permanent 控件**——`QStatusBar::showMessage()` 会隐藏所有普通控件（`addWidget` 添加的），用普通控件的话它会在每次状态消息出现的几秒里消失，而那恰恰是最需要看到它的时刻。

### 超时自动后台化

前台命令超时**不再一律杀掉**：有后台任务支持时，它会被自动转入后台，把控制权还给模型，让它去做别的事、稍后再用 `TaskOutput` 读结果（对应 `assistantAutoBackgrounded`）。结果里会带 `assistantAutoBackgrounded: true`，与模型/用户显式要求后台化的情形区分开。

转交时要处理三件事，缺一不可：停掉前台定时器（否则中断轮询会杀掉一个已经归后台所有的进程）、断开前台挂在该进程上的全部处理器（否则前台读取器继续抢输出，`finished` 处理器还会 `deleteLater` 掉一个已经不属于它的进程）、把前台已读到的输出带进后台记录（历史不丢）。

### 跨重启恢复

后台任务要**活过宿主退出**，就不能让输出走管道——宿主退出后管道读端关闭，子进程再写会拿到 EPIPE。所以：

| 机制 | 做法 |
| --- | --- |
| 启动方式 | `QProcess::startDetached`，**不持有** `QProcess`。这是硬要求：`~QProcess` 会杀掉仍在运行的进程，"活过宿主"就无从谈起 |
| 输出 | 由 shell 自己重定向到日志文件，全程没有管道。POSIX 用 `{ …; } >> log 2>&1`；PowerShell 用 `*>> log`（一条重定向覆盖所有流）；cmd 用 `>> log 2>&1` |
| 退出码 | 分离式任务没有 `wait()` 可取退出码，所以让 shell 把退出码写到 `<log>.exit` 旁路文件。POSIX 是 `echo $?`；PowerShell 取 `$LASTEXITCODE`（纯 cmdlet 失败时落到 1）；cmd 是 `%errorlevel%` |
| 账本 | `<数据目录>/tasks/ledger.json` 原子写入，记录 id/pid/启动指纹/输出路径/状态 |
| 重启对账 | 启动时按 `pid` + **启动时间指纹**判断是否还活着：活着则认领并轮询其输出文件；已结束则标记 `lost`，退出码如实记 -1，**不猜一个 0 让模型以为成功** |

存活判定与终止按平台实现：

| 平台 | 存活判定 | 终止整棵进程树 |
| --- | --- | --- |
| Unix | `kill(pid, 0)`，`EPERM` 视为存活 | `kill(-pid)` 杀进程组 + `kill(pid)` |
| Windows | `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess`，`STILL_ACTIVE` 即存活 | `taskkill /PID <pid> /T /F` |

Windows 的启动指纹取不到（只有 Linux 实现读 `/proc/<pid>/stat`），所以 pid 复用校验在 Windows 上不生效——这是**已知边界**，不是疏漏。

### 两种后台任务

这不是实现取巧，是 spawn 方式决定的：

| | 分离式（显式 `run_in_background`） | 管道式（超时自动后台化） |
| --- | --- | --- |
| 输出 | 直接写文件，无管道 | 继承前台管道 |
| 跨重启 | **可以**，由账本认领 | **不可以**，宿主退出即拿不到输出 |
| 退出码 | 由旁路文件取得 | `QProcess` 直接给出 |

管道式任务无法在启动后改重定向，所以它只在本进程存活期间继续运行。需要跨重启就用显式 `run_in_background`。宿主退出时会对管道式任务明确告警，不假装它还能活。

### 已知限制

`TaskStop` 对分离式任务按 pid 终止整棵进程树（Unix 发进程组信号，Windows 走 `taskkill /T`），因此**只能终止仍然存活的进程**；进程已自行退出时按 `lost` 收尾。Unix 上还有启动指纹校验，pid 被复用时能拦住误杀；Windows 没有指纹（见上一节），这是当前的边界。此外，分离式任务不会继承宿主的环境变更，输出也不区分 stdout/stderr（合并写同一份日志，因为 QProcess 无法把两条流落到同一句柄）。

## 子 Agent

`Agent` 工具（别名 `Task`，Claude Code 兼容别名一致）把一个自包含的子任务交给
**独立的子会话**去做。全部价值在上下文隔离：子代理跑十几轮工具调用的中间过程不会污染父代理的
上下文，父代理只拿到一段结论加一行用量摘要。

| 维度 | 实现 |
| --- | --- |
| 上下文 | 子代理有全新的 `Session` 与消息历史；父代理的消息列表里**不会**出现子代理的对话 |
| 系统提示词 | 用子代理身份与职责说明（`subagentIdentitySection`），不是主代理身份 |
| todo | 父子各有独立的 `TodoStore`，互不覆盖 |
| 工具面 | 由 profile 决定；`Explore` 用白名单收窄到只读工具 |
| 权限 | **共享同一个 `PermissionGate`**：谁有权限只有一个判定点，UI 只需向一个入口提交裁决 |
| 回传 | 子代理**最后一条**有正文的 assistant 消息 + `<usage>subagent_tokens / tool_uses / duration_ms</usage>` |
| 步数上限 | 子代理 12 个模型步（见下方说明） |
| 递归 | **禁止**：子代理再调 `Agent` 会被明确拒绝 |
| 界面 | 子会话作为独立会话落盘并出现在侧边栏（标注「子代理」），但**不会**抢走当前会话 |

两个 profile：

| id | 只读 | 工具面 | 用途 |
| --- | --- | --- | --- |
| `general-purpose`（默认） | 否 | 继承父代理完整工具面 | 需要实际改代码的任务 |
| `Explore` | 是 | 仅 `Read` / `Glob` / `Grep` / `TodoRead` | 调研，不动手 |

`Explore` 是**两道独立闸门**：白名单让模型从一开始就看不到写工具，同时子会话跑在 `Plan` 模式下，
即使模型凭历史记忆直接调用写操作也会被运行时拒绝（返回 `tool_not_allowed`）。

关于步数上限：本实现的子代理 `maxTurns` 默认 4，按"turn"计数（一次模型响应 + 它的工具批）；
本实现按"模型步"计数（一步 = 一次模型响应），一次工具往返需要两步，所以 4 轮工具往返约等于
12 步，取 12 作为等价上限。触及上限时会在回传内容里带上 `<warning>`，让父代理知道结论可能不完整。

未实现的部分（明确列出）：`run_in_background` 后台子代理会**明确返回不支持**而不是假装启动；
没有 `SendMessage`，所以不能向已结束的子代理追加消息（父代理需要重做就只能重新派生）；
子代理继承父代理当前的模型快照，暂不支持为子代理单独指定模型。

## Read 读图片

`Read` 遇到图片文件（按 MIME 判定）不会当作二进制拒绝，而是把图片**作为图片内容块**返回给模型，模型可以直接看图回答，不需要借助外部命令。

这一点之前是坏的：`Read` 确实有图片分支，但只把 base64 塞进 `metadata`，模型收到的是一行 `Image read: … (image/png, 832 bytes)` 文字、看不到任何像素，于是它会退回去用 `Bash` + Python（PIL / `file`）去猜图片内容。

修好它需要三处都通，缺一不可：

| 环节 | 做法 |
| --- | --- |
| `ToolResult` | 新增 `images`（`QList<FilePart>`），**不放在 metadata 里**——metadata 只会变成文字 |
| 工具结果消息 | 除了 Tool part，还要为每张图追加一个 **File part**：provider 的图片序列化只认 File part，图只挂在 Tool part 上模型依然看不见 |
| 持久化与界面 | `ToolPart::images` 随 part 一起进 SQLite，工具卡片直接渲染缩略图，重启后还在 |

两个 provider 都不需要额外改动：图片以 File part 进入工具结果消息后，走的就是普通图片附件那条序列化路径（Anthropic 的 `image` 块 / OpenAI 的 `image_url`）。

## MCP（stdio）

在 `settings.json` 里配置 MCP 服务器，应用启动时把它们作为子进程拉起，服务器报告的工具会**注册成普通工具**——模型看到的 MCP 工具与内置工具没有任何区别（同一套声明、权限链、并行调度、结果渲染）。

```json
"mcpServers": [
  {
    "id": "github",
    "command": "npx",
    "args": ["-y", "@modelcontextprotocol/server-github"],
    "env": ["GITHUB_TOKEN=ghp_xxx"],
    "enabled": true
  }
]
```

| 设计点 | 理由 |
| --- | --- |
| stdio + **换行分隔**的 JSON-RPC 2.0 | 这是 MCP stdio 传输的规定，不是 LSP 的 `Content-Length` 头 |
| 严格按协议握手 | `initialize` → `notifications/initialized` → `tools/list`。少发那个通知，不少服务器会直接拒绝后续请求（假服务器就复现了这一点） |
| stdout 上的**非 JSON 行跳过** | Node 生态的服务器常往 stdout 打人类日志；当成致命错误会让整套集成"连不上"且毫无线索 |
| 按 `id` 匹配响应 | 响应到达顺序不保证与请求一致，按顺序配会串台；同时要把**通知**（无 id）和响应区分开 |
| 工具名 `mcp__<server>__<tool>` | 避免不同服务器的同名工具互相覆盖，也让模型/用户一眼看出信任边界 |
| 工具名过滤非法字符 | 服务器返回的名字带空格或斜杠时，不少 provider 会直接拒收工具声明 |
| 入参 schema **原样透传** | 修补 schema 会让模型看到的入参与服务器期望的不一致，报错很难定位 |
| 权限默认**保守** | 远端工具对我们不透明：没声明就按 `System` 处理（每次都要确认）且独占执行 |
| `readOnlyHint` 只在**放宽**方向采信 | 那是服务器自述，不是可信信息；用它来收紧等于把权限交给一个我们不审计的进程 |
| `isError` 与协议错误分开 | MCP 用 `isError` 表达"工具自己报告失败"，必须映射成工具失败，而不是"调用成功但内容写着拒绝" |
| 超时兜底 | 请求 20s、握手 30s；服务器卡死时不能让工具调用永远挂着 |
| 退出时 `stopAll` | 子进程必须显式终止，否则退出后留孤儿 |

握手是**异步**的，但界面会在第一次发送前等它就绪（上限 8 秒）：工具声明是每次请求重新构建的，所以第一次请求如果赶在握手完成之前发出，模型这一次就看不到 MCP 工具——它会以为自己没有这些能力，而用户明明配了。等待有上界，卡住的服务器不该把用户的输入也一起卡住。

**当前范围**：只做了 stdio 传输与 `tools` 能力。剩余的 MCP 缺口（HTTP/SSE、`resources`/`prompts`、设置界面）统一记在文末的「已知未实现 / 部分实现」一节——范围声明只留一处，避免两处描述各自过期。

## 设置界面（MCP / Skills）

设置对话框里新增一页「MCP / Skills」，两者都是"外部能力接入"，放在一起：

| 区域 | 能做什么 |
| --- | --- |
| MCP 服务器 | 表格列出名称/命令/参数/启用；添加、编辑、删除。编辑走一个小对话框（5 个字段含多行的 args/env，塞进表格单元格里编辑很难受） |
| Skills 目录 | 列出搜索目录；添加、移除、恢复默认；**当场预览**认到了几个技能 |

几个刻意的处理：

| 决定 | 理由 |
| --- | --- |
| 名称与命令为空时禁用「确定」 | 缺任何一个服务器都起不来，与其存下去再报错不如拦在入口 |
| 环境变量少写 `=` 时明确报错 | 格式错的行会被运行时忽略，用户会以为已经生效 |
| 名称重复时拒绝并提示 | 重名会让工具名前缀撞车，注册表里互相覆盖 |
| 添加目录时先把默认目录并进来 | 用户点「添加」的意图是"再加一个"，不是"丢掉默认的那两个" |
| 移除默认目录时先展开成显式列表 | 否则删掉一个默认目录后，"空列表 = 用默认"的语义会把它又加回来 |
| 保存后立刻重连 MCP、重扫技能 | 否则用户会以为配置没保存（要等重启才生效） |
| 技能目录做实时预览 | 让用户当场确认目录被认到了，而不是等重启后发现一个技能都没有 |

配置仍在 `settings.json` 里（`mcpServers`、`skillDirectories`），界面只是它的编辑器；`skillDirectories` **为空表示用内置默认**（用户级 + 项目级）。

## Skills

Skill 是一份**可复用的指令包**：一个目录里放 `SKILL.md`，带 name/description 与正文。

```
<数据目录>/skills/pdf/SKILL.md      ← 用户级
<工作区>/.lycode/skills/pdf/SKILL.md ← 项目级（同名时覆盖用户级）
```

```markdown
---
name: pdf
description: 处理 PDF 文件：抽取文本、拆分、合并
---

（正文：具体步骤与命令）
```

| 设计点 | 理由 |
| --- | --- |
| 提示词里**只放名字 + 描述**，正文用 `Skill` 工具按需加载 | 几十个 skill 的正文会把上下文塞满，而这正是 skills 机制要解决的问题（有测试专门断言正文**不**出现在提示词里） |
| 两种布局都认：`<name>/SKILL.md` 与 `<name>.md` | 目录式便于附带脚本等附属文件，扁平式适合一句话技能 |
| 项目级覆盖同名的用户级 | 项目级更具体，应当胜出 |
| 目录不存在就跳过 | 技能目录是可选配置，不是错误 |
| frontmatter 只认单行 `key: value` | 不引入 YAML 解析器：为这么简单的元数据拉一个依赖不值得，而且一旦支持嵌套，用户就会开始写解析器不完整支持的东西 |
| `---` 只在**第一行**才算 frontmatter | 否则一段以分隔线开头的正文会被静默吃掉 |
| 没有 frontmatter 时名字取目录名、描述取正文第一行 | 清单里总得有点说明，否则模型只看到一个名字，无从判断该不该加载 |
| 找不到技能时**列出可用的名字** | 模型偶尔会记错名字，一次就能纠正，而不是反复试错浪费上下文 |
| `Skill` 工具只读、免确认 | 它读的是本地指令文件，改变的是模型接下来的行为，不碰工作区 |

## 会话标题由模型生成

回合正常结束后，用模型把首条用户输入浓缩成一个具体标题（提到涉及的文件/功能/报错），而不是机械地取前 40 个字符。

| 设计点 | 理由 |
| --- | --- |
| **独立于主回合的轻量请求** | 不阻塞对话；结果不进消息历史，不污染上下文 |
| 不给工具 | 纯文本改写任务，给了工具模型会试图去读文件 |
| `maxOutputTokens = 64`、`temperature = 0.3` | 给多了它会开始解释，温度高了标题会飘 |
| 素材取首条**用户可见**消息 | `modelOnly` 的合成轮（工具结果、后台任务通知）不是用户说的话，拿它当素材会生成出莫名其妙的标题 |
| 幂等 | `Session::titleGenerated` 标记 + 在飞标志，一个会话只生成一次 |
| 清洗 | 剥前缀（`标题：`/`Title:`）、markdown 符号、成对包裹符号（含中文 `「」【】`），**循环到稳定**——这些符号是嵌套的，`**"标题"**` 只过一遍会剩下 `"标题"**` |
| 清洗失败就保留原标题 | 宁可留着机械标题，也不要一个空标题或一串标点 |

**可以在设置里关掉**（默认开）：它意味着每个新会话多一次模型调用。关掉后标题退回"取首条输入的前 40 字符"，无需联网、零成本。

## 代码语法高亮

Markdown 代码块里的代码会着色：注释、字符串、关键字、类型、数字、函数名、预处理指令七类。

环境里没有可用的高亮库（Qt 不自带，也不引入额外第三方依赖），而对话里的代码以**片段**为主——需要的是"扫一眼分清字符串/注释/关键字"，不是逐像素还原某个编辑器主题。所以写了一个单遍扫描的轻量分词器。

| 设计点 | 理由 |
| --- | --- |
| 单遍字符扫描，不用正则 | 正则版本在长行上会出现灾难性回溯，而代码块长度不可控（用户可能贴几千行） |
| 字符串/注释**优先于**关键字 | 否则 `"for"` 里的 for、`// for` 里的 for 都会被染成关键字色。这是最容易做错的地方 |
| 单双引号字符串不跨行 | 跨行通常是漏了引号，继续吃下去会把后面整段代码染成字符串 |
| 预处理指令只在行首 | `a # b` 里的 `#` 不是指令 |
| 认不出就退回纯文本 | 高亮是锦上添花，**内容完整性是底线**；测试断言"去掉 span 并反转义后与原文本完全一致" |
| 未知语言按 C 系兜底 | 兜底规则**不**把 `#` 当注释：未知语言里 `#` 可能是运算符，误判比不着色更糟 |

支持 C/C++/Java/C#/Rust/Go/Swift/Kotlin、Python、JavaScript/TypeScript、Shell、JSON、SQL、CMake；别名归一化（`c++`/`py`/`ts`/`console` → 对应语言）。

### 一个曾经"全绿但完全没生效"的链路

会话视图原本用的是 `QTextBrowser::setMarkdown()`——**Qt 内置的 Markdown 解析器**，而自研的 `Markdown::toHtml()` 只在单元测试里被调用过。后果是：

* 语法高亮（`tok-*` span）永远不出现
* `div.code-block` / `pre.code` 这些类选择器对不上，代码块样式失效
* 自研的表格、任务列表、链接协议白名单统统不生效

而测试全是绿的：单元测试直接调 `Markdown::toHtml`（当然过），截图测试用独立的 `QTextBrowser`（也过）。**没有任何测试走过会话视图这条真实渲染路径。**

现在会话视图改为 `setHtml(Markdown::toHtml(source, style))`，并补了一条专门盯这条链路的测试：构造一条含 cpp 代码块的 assistant 消息丢进 `ConversationView`，断言渲染后的文档**真的有多种前景色**。把实现换回 `setMarkdown` 时这条测试会如实失败（只剩 1 种颜色）。

**颜色走内联 `style` 而不是 CSS 类**——这一点是实测出来的：Qt 富文本的 CSS（`QTextDocument::setDefaultStyleSheet`）对选择器支持很窄，`span.tok-keyword { color: … }` 和 `.tok-keyword { … }` **都不生效**，而同文件里 `pre.code`、`div.code-block` 这类元素+类选择器是生效的。与其继续试探选择器形状，不如把颜色写进 span 的内联样式。`class` 仍然保留，供识别与测试使用。

另外，语法配色**不是** 本实现的设计令牌——本实现的 UI 变量里没有语法配色（Diff 那组是唯一例外）。这里用的是编辑器风格的常用取值（One Light / One Dark 一族），挑选标准是与本主题代码背景的对比度、以及彼此色相可区分。

## 点击查看文件与图片

工具卡片里的内容是**给模型看的**：正文被 output 预算截断、输出框限高、图片只画 240px 缩略图。用户要核对"到底读到了什么"时需要一个出口：

| 入口 | 行为 |
| --- | --- |
| 图片缩略图（整块可点，`PointingHandCursor`） | 打开查看器，按窗口大小适配显示原图；副标题给出 MIME、**原始像素尺寸**与体积 |
| 「查看文件 xxx ▸」（Read / Write / Edit 有 `filePath` 时出现） | 打开完整文件内容，等宽字体 + 行号栏 |

查看器的几个取舍：

| 决定 | 理由 |
| --- | --- |
| 图片**不放大**小图 | 放大只会变糊，没有信息增量；大图按窗口缩放 |
| 代码**不折行** | 折行会让一个逻辑行占多行，行号与内容就对不上了 |
| 行号栏独立成控件 | 画在 viewport 里会随横向滚动一起滚走 |
| 行号宽度按最大行号位数算 | 固定宽度要么裁掉 4 位数行号，要么留一大片空白 |
| 只画可见块的行号 | 整文件逐行画在长文件上会明显卡顿 |
| 打开时定位到开头 | 否则长文件会停在末尾，用户以为内容不对 |
| 文本上限 4 MB | 再大就不该在窗口里看，明确引导用系统程序打开 |
| 代码视图**也着色** | 与 Markdown 代码块**共用同一个分词器**（`SyntaxHighlighter::tokenize`），只是渲染端不同：富文本走 HTML，`QPlainTextEdit` 走 `QTextCharFormat` |
| 不断言代码块背景色 | Qt 富文本对 `div` 上的 `background-color` 支持不可靠（实测没变成块背景画刷），断言它只会得到一条时好时坏的测试 |
| 整篇一次性分词（非逐行） | `QSyntaxHighlighter` 逐行回调处理不了块注释这类跨行结构；整篇分词后按 token 区间上色，跨行结构天然正确 |
| 语言按**扩展名**猜 | MIME 对 `.h`/`.cpp`/`.m` 给的是很粗的类别，分不出该用哪套关键字表 |
| 读不到内容时给出明确说明 | 空白窗口会让用户以为"文件是空的"，而实际上根本没读到 |
| 「用系统程序打开」仅在文件确实存在时出现 | 想编辑或想用专门的图片工具看时的出口 |

图片查看器直接接收**解码后的字节**而不是路径：粘贴进来的图片没有磁盘路径，只有字节才能保证一定能显示。

## Diff 视图

`Write` / `Edit` 会把改动生成为结构化补丁写进 `metadata.structuredPatch`。此前没有任何控件消费它，用户看不到"到底改了什么"；现在工具卡片里有一块专门的渲染区。

| 设计点 | 理由 |
| --- | --- |
| 用 `structuredPatch` 而不是重新解析文本 diff | 每行自带 `type`，渲染端不会因为格式细节（`\ No newline`、行号宽度）出现展示偏差 |
| 增删行用**背景色块**而非 `+`/`-` 前缀 | 深色主题下满屏前缀几乎看不出结构，色块才能一眼扫出改动范围 |
| 未变行**不给**背景 | 背景只用来标出"改了什么"，全都有底色等于没有重点 |
| 两侧行号 + 不折行 | 折行会让一个逻辑行占多行，行号就和内容对不上了 |
| 单次最多渲染 400 行 | 一个改动几千行的补丁不该撑爆对话流；超出时明确显示剩余行数 |
| 统计按**完整**补丁算 | 被截断的是显示不是事实。先判预算会让 5000 行的改动显示成 "+400 −0"，严重低估规模 |

文件内容一律 HTML 转义：源码里的 `a < b`、HTML 模板里的 `<script>` 不转义会被当成标签吃掉。

## 图片附件

输入区左下角的「图片」按钮、`Ctrl+V` 粘贴截图、把图片文件拖进输入框——三条入口都落在同一个 `attachImages()` / `attachImageData()` 上。附件以缩略图 + 文件名显示在输入框**上方**（它们属于"这次要发什么"，必须紧贴输入框），每个都带移除按钮；发送成功后清空，失败则保留。

| 环节 | 做法 |
| --- | --- |
| 待发状态 | `pendingAttachments_`，属于"这次编辑"，切换会话时作废 |
| MIME 判定 | `QMimeDatabase::mimeTypeForFileNameAndData()`，**不按扩展名硬编码**——png 存成 `.jpg` 会让 `media_type` 与实际字节不符，两个 provider 都会拒绝 |
| 剪贴板 | `QImage` 统一转 PNG 再编码，理由同上 |
| 上限 | 单张 8 MB（base64 后还要进 SQLite 与 HTTP body） |
| Anthropic | `{"type":"image","source":{"type":"base64","media_type":…,"data":…}}` |
| OpenAI | `image_url` + `data:<mime>;base64,…`；**无图片时 content 保持纯字符串**，数组形式并非所有兼容服务都实现了 |
| 渲染 | 对话流里画缩略图（最大边长 320），而不是只显示文件名 |

两个容易踩的点：非图片附件会**明确告警后跳过**（静默丢弃会让用户以为文件已经给模型看过了）；`Part::isEmpty()` 对 File 必须把 `base64` 计入载荷，否则粘贴来的图片（没有磁盘路径）会被判成空 part，图发出去了但界面上什么都看不到。

未实现：非图片文件附件（PDF/文本等）、一次发送的附件数量上限、图片压缩/缩放。

## 让用户选一个

需要用户在几个方案里挑一个时，界面会把它渲染成**可点的按钮**（位置在输入框上方），点一下把选项填进输入框。

**格式是约定的，不是猜出来的**：

````
```choices
- 只改 Read 工具
- 同时改 Read 与 Grep
```
````

系统提示词里明确要求模型用这个 `choices` 围栏块输出（2–6 项、每项一行且不超过 40 字、块内不写解释）。

| 决定 | 理由 |
| --- | --- |
| 约定格式，而不是解析正文里的编号列表 | 猜必然误判——"步骤如下：1. 2. 3."、目录、并列要点都会被变成按钮，正常的回答看起来像在逼用户做选择。约定格式后解析变成精确匹配，误判消失 |
| 只认**最后**一个 `choices` 块 | 翻看历史时不该把上一轮的选项又摆出来 |
| 该块渲染成**列表**而不是代码块 | 否则同一批选项会在正文里出现一次、又在按钮里出现一次 |
| 点选后**填入输入框**而不是直接发送 | 用户还能改一改再发，也避免误点直接发出 |
| 换会话时收起 | 旧选项不该留着 |

`Markdown::detectChoices()` 是纯函数，`test_markdown` 覆盖了正例与**反例**（普通编号步骤、单项、超过 6 项、非 `choices` 的普通列表都不该被识别）。

## 应用图标

品牌蓝圆角方块 + 白色终端提示符 `>_`。选这个组合是因为它在 **16px** 下仍可辨——那是最小的真实使用尺寸（任务栏/窗口标题栏）；更复杂的图形缩到 16px 都会糊成一团。

**资源目录镜像安装目录**，清单只有一份：

```
assets/icons/linux/hicolor/16x16/apps/lycode.png   →  /usr/share/icons/hicolor/16x16/apps/lycode.png
assets/icons/linux/hicolor/512x512/apps/lycode.png →  /usr/share/icons/hicolor/512x512/apps/lycode.png
assets/icons/windows/lycode.ico                     →  编进 exe（Windows 资源）
assets/icons/windows/win_resources.rc
assets/resources.qrc
```

| 决定 | 理由 |
| --- | --- |
| 资源树与安装树一一对应 | `install(DIRECTORY ...)` 直接照搬整棵树，不必逐档列文件名；加一档尺寸时 CMake 不用改 |
| 用 `AUTORCC`（qrc 当源文件列进目标） | ⚠ `qt_add_resources` 在 Qt 6 里两种写法都**静默失败**：第二个参数是资源名而非 `.qrc` 路径（传路径什么都不生成），放进 `FILES` 则把 `.qrc` 本身当一个普通文件内嵌、不解析里面的 PNG。⚠ 而 `CMAKE_AUTORCC` 必须**在创建目标之前**设置，它只在目标创建时被读取 |
| 附带 `.ico` + `.rc` | 只靠 `setWindowIcon` 不够：那只影响运行中的窗口，**exe 文件本身**在资源管理器里显示的图标来自编译进去的 Windows 资源 |
| Windows 走 .ico，其他平台走 PNG | `.ico` 本身就是多尺寸容器（实测 Qt 的 ICO 插件会把 16–256 七档都报给 `QIcon`），且与编进 exe 的那份资源同源——运行中的窗口与文件图标不会有两套图像。512 那一档 Windows 用不到 |
| 资源挂在 `lycode_lib` 上 | 测试链接的是这个目标，资源跟着它才能被测试验证到 |
| 内嵌而不是运行时读文件 | 装完后二进制与 `assets/` 的相对位置会变（`bin/` vs `share/`），按路径查找迟早出错 |
| 图标不随主题变色 | 应用图标是**品牌标识**，不该跟着界面明暗主题变 |

`.ico` 是脚本生成的 ICO 容器（内嵌各档 PNG），不需要额外工具。`test_ui_flow` 会断言八档齐全、且 16px 那档能看到白色笔画——漏一档或图糊了都会在测试里报出来。

## 侧边栏：工作区 → 会话树

左侧是两层树：顶层是工作区，子节点是它的会话。

```
▾ LyCode-qt                    ← 工作区（可折叠）
    run echo test
    核对日志
      子代理 · 子代理结论：没有异常。
▸ other-project
```

顶部**没有**单独的工作区切换行：工作区就是树本身。顶部只留一个「打开工作区…」按钮（与菜单栏同一个动作、同一个措辞）；新建**会话**的入口在每一行工作区右侧的 `+` 上——"在哪建"这个信息本来就属于那一行。

措辞是"打开"而不是"新建"：目录本来就在磁盘上，这个动作是把它**加进工作区列表**，不是创建它。同一个动作在菜单栏和侧边栏不该有两个名字。

工作区节点的右键菜单只有两项：从最近列表移除 / 删除该工作区全部会话。

**展开/折叠只是界面收起，不是"打开/关闭工作区"**，所以菜单里没有"打开"。要切到某个工作区，点它下面的会话即可（会先切工作区再打开那个会话），或点它右侧的 `+` 在该工作区新建一个会话。

展开状态会**持久化**：下次打开软件时，你上次展开的那几个工作区仍然是展开的（会话按需重新加载）。首次运行时只展开当前工作区——全部展开会在启动时把每个工作区的会话都查一遍，最近列表长的时候会拖慢启动。

| 设计点 | 理由 |
| --- | --- |
| 用树而不是"工作区按钮 + 当前工作区的列表" | 用户要同时看到**多个**工作区各自有哪些会话，平铺列表只能显示当前那一个 |
| 会话入口挂在**工作区行**上，不是顶部 | 点的是那一行，期望落点也在那一行；顶部的"新建会话"只能作用于当前工作区 |
| 点其它工作区的 `+` 时先切过去 | 否则新会话会建到别的工作区，与用户的点击对象不符 |
| 会话**懒加载**（展开工作区时才查库） | 启动时不为每个最近工作区都查一次库，最近列表长的时候会拖慢启动 |
| 展开状态持久化 | 否则用户展开过的工作区每次重启都被收起来，看起来就像"只有一个工作区是打开的" |
| 重建顶层节点时**复用**已有 item | `clear()` 会销毁 item 并丢掉展开状态与滚动位置，用户每切一次会话就要重新展开一遍 |
| 打开其它工作区的会话时**先切工作区** | 否则会话会被载入到不匹配的工作区上下文里（工具的工作目录、会话列表都是错的） |
| 选中会话前先展开它的父工作区 | 折叠状态下选中一个看不到的节点，用户会以为点击没反应 |
| 工作区节点右键菜单**没有**"打开" | 展开/折叠只是界面收起，不是打开/关闭工作区；切换靠点它下面的会话 |
| 展开指示符**自己画**（`▸` / `▾`），点击节点切换折叠 | ⚠ 一旦给 `QTreeView` 设了样式表，Qt 就改用 `QTreeView::branch` 画箭头，而它默认没有图像资源——箭头会整个消失。换文字指示符后又没有可点的箭头，所以必须自己接点击事件，否则用户**根本没法折叠** |
| 指示符**无条件显示**，不看 `childCount()` | ⚠ 会话是懒加载的，没被展开过的工作区 `childCount()` 就是 0。按它判断会让这些工作区既没有 `▸` 也没有 `▾`，看起来根本不能折叠（用户报的"重启后有些工作区没有向右也没有向下"）。空工作区多一个 `▸` 无所谓，"看不出能不能点"才是真问题 |
| 树的 item 要显式 `margin: 0` | ⚠ 全局样式表里有 `QTreeView::item { margin: 1px 4px; border-radius: 8px; }`，它按**单元格**把背景内缩。会话行第二列是空的（那一列只给工作区放 `+`），于是同一行被画成左右两个独立圆角块——**右侧**那个色块的成因 |
| 关掉 Qt 自带的树枝装饰（`setRootIsDecorated(false)`） | ⚠ **左侧**那个色块的成因。展开指示符已经自己画了，Qt 的装饰是多余的，而且它在深色主题下会画出一小块底色，紧贴在选中行左边 |
| 操作列宽度要在**条目建好之后**再设一次 | ⚠ 表头会在插入带 `itemWidget` 的条目时按内容重算，把 22px 撑成 40px。实测这一下白吃掉 18px 正文宽度，会话条目第二行几乎整行变成省略号 |
| 侧边栏默认宽 300（原 260） | 树有缩进，右侧还要留操作列。260 时正文只剩 190px，条目读不出内容 |
| 会话条目**只显示标题，一行** | 曾经把"最后收到的消息"作为第二行：一是每条会话都很占高度，二是那段摘要要先做 markdown 去标记再截断才能勉强读，信息量低却抢走一半可视面积。消息内容看右侧对话流即可。状态徽章（待确认/运行中/子代理/出错）合并到同一行——它是有行动价值的信息 |
| 启动时的工作区也写进列表 | 否则它只以"当前工作区"的身份出现在树上，一旦切到别的目录就从树上消失，用户会以为工作区被删了 |
| 切换工作区**不**改变树的顺序 | 原先按"最近使用优先"排（每次切换都提到最前）。那是给已删除的顶部切换菜单用的；现在树上显示的就是这个顺序，再排序会让用户正在点的条目在眼皮底下跳走 |

## 工作区管理

侧边栏顶部的工作区按钮点开后，**每个工作区一个子菜单**（不是平铺的一串条目——一个菜单项只能有一个触发动作，而每个工作区有三件事要做）：

```
当前：LyCode-qt  —  /home/u/LyCode-qt ▸  ├ 从最近列表移除
                                       └ 删除该工作区的全部会话…
─────────────
other-project  —  /home/u/other   ▸  ├ 打开
                                     ├ 从最近列表移除
                                     └ 删除该工作区的全部会话…
─────────────
选择其它目录…
```

| 动作 | 做什么 | 不做什么 |
| --- | --- | --- |
| 从列表移除 | 从 `recentWorkspaces` 去掉，落盘。移除的是**当前**工作区时，先切到列表里剩下的第一个再移除——否则"当前工作区"会被强制补回树上，看起来毫无变化 | **不碰任何会话**，下次打开该目录会重新出现 |
| 从树里点会话切工作区**不写回列表** | 那个工作区可能正是用户刚移除的，写回等于让它复活（`openWorkspacePath(path, remember=false)`） | 只有"用户显式打开"才写回列表 |
| 移除时清掉该工作区的**索引型配置** | `workspaceLastModel`（按工作区 key 记住的模型）、`expandedWorkspaces` 都要一起删。它们按工作区索引，不清就会在 `settings.json` 里长期堆积已经删除的工作区；启动时还会对账一次，清掉旧版本遗留的孤儿记录 |
| 移除最后一个工作区 | **允许**。删完进入"无工作区"状态：会话与对话流收干净、`workspace_` 与 `lastWorkspace` 清空、发送按钮自动禁用、界面提示去「打开工作区…」 | 见下方说明 |

**"没有工作区"是一个被完整支持的状态**，不是"半坏"。为此这几条路径都加了守卫：

| 路径 | 处理 |
| --- | --- |
| `onNewSessionRequested` | 无工作区时**用状态栏提示**，不用模态框——模态框会让任何走到这里的路径都停下来等人点确定（实测把测试卡死） |
| `openSessionOrCreate` / `loadWorkspaceSessions` | 无工作区时直接置空。**绝不调用 `listSessions("")`**：空 key 的语义是"不过滤"，会返回**所有**工作区的会话 |
| `SidebarPanel::ensureWorkspaceItem` / `upsertSession` | 空路径不建节点、不插入会话，避免树上出现没有名字的顶层项 |
| 启动 | 没有任何工作区时**不**用当前目录兜底——那会让"移除最后一个工作区"在重启后复活。停在无工作区状态 |

**从树里点会话切工作区时不写回列表**（`openWorkspacePath(path, remember=false)`）：那个工作区可能正是用户刚从列表移除的，写回等于让它复活。只有"用户显式打开"才写回。
| 删除该工作区的全部会话 | 二次确认后按 workspace key 调 `deleteSessionsForWorkspace()` | **不删磁盘上的目录和文件** |

两者刻意分开：用户说"删除工作区"时往往以为会删磁盘目录。确认框里明确写了"工作区目录本身和其中的文件**不会**被删除"，避免误操作。

删空当前工作区之后会立刻开一个新的空会话（否则界面没有可用的活动会话，后续落盘会一路报外键失败）。删的是**会话记录**，所以断言写的是"旧会话 id 都不在了"，而不是"一条都不剩"。

## 工具并行调度

同一次模型响应里可能要求多个工具调用。调度规则本实现的 `ToolScheduler` + `batch-runner`：

```
调用序列（模型给出的顺序）:  Read   Grep   Write   Read   Edit
分组结果:                    └── 组 1 ──┘  组 2   组 3  组 4
                             组内并行      独占    独占   独占
执行:                        组间串行 ──────────────────────→
```

| 规则 | 说明 |
| --- | --- |
| 组内并行、组间串行 | 同一组内同时执行，上一组全部结束才开下一组 |
| 组内上限 | `kMaxToolConcurrency = 10`（与 本实现的默认 `maxConcurrency` 一致） |
| 独占组 | `canRunInParallel() == false` 的工具单独成组，与前后调用形成串行屏障 |
| 终止语义 | 某调用要求终止本轮时，**等同组兄弟全部结束**再中断后续组 |
| 失败不截断 | 一个工具失败只影响它自己的结果，后续组照常执行 |

**并发策略是三态**（`ToolMetadata::Concurrency`）：`Safe` / `Serial` / `Unspecified`。这一点很关键——本实现里 `concurrentSafe` 是 `boolean | undefined`，用 C++ 的 `bool` 会把"显式声明必须串行"和"未声明"混为一谈，于是显式声明串行的**只读**工具会被"只读且无副作用 ⇒ 可并发"的豁免分支错误放行。这个缺陷是在写并行测试时被真实暴露出来的。

内置工具的分类：`Read` / `Glob` / `Grep` / `TodoRead` 可并发；`Bash` / `Write` / `Edit` / `TodoWrite` 串行（`Bash` 破坏性，`TodoWrite` 虽然 `readOnly` 但会写会话状态）。

与 本实现的差异：本实现的调度器还做依赖图的拓扑排序，因为工具可以声明 `dependencies`。本实现的工具不声明依赖，顺序约束只来自模型给出的调用次序，所以"顺序扫描 + 独占组"就是完整语义，不需要拓扑排序。

**结果顺序与完成顺序无关**：回灌给模型的工具结果始终按模型给出的调用次序排列，所以并行不会让对话历史变得不确定。

## 用量明细

状态栏右侧显示四个缓存相关指标（会话累计）：

```
就绪            上下文 44 / 1.0M ▬▬▬   缓存 71% · 未缓存 300 · 缓存读 750 · 输出 50
```

| 指标 | 含义 |
| --- | --- |
| **缓存命中率** | `缓存读取 /（缓存读取 + 未缓存输入）` |
| **未缓存** | 真正要模型从头处理的输入 token |
| **缓存读** | 命中缓存、直接从缓存读取的输入 token |
| **输出** | 生成的 token |

悬浮提示里给出四个字段的精确数字、会话累计与**最近一轮**的对比，以及命中率的分母口径。

两点值得说明：

- **分母不含"缓存写入"**。那是首次写入缓存的部分，本来就没有机会命中；算进分母会系统性低估命中率。
- **两种协议的口径已经归一**。Anthropic 的 `input_tokens` **不含**缓存部分（读/写单列），OpenAI 的 `prompt_tokens` **含**缓存部分（`prompt_tokens_details.cached_tokens`）。如果照原样落进同一个字段，同一个 `inputTokens` 就有了两种含义、命中率必然算错。现在统一为「`inputTokens` = 未命中缓存的输入」，OpenAI 路径会减掉缓存部分（并对 `cached > prompt` 的脏数据做 clamp）。

## 输入区布局

模型、思考等级、模式三者都在**输入框下方那一行**，而不是顶部工具条——它们影响的是"这一次发送"，贴着输入框才符合"先设参数再发送"的顺序：

```
┌──────────────────────────────────────────────────────┐
│  描述你想完成的任务…（Enter 发送，Shift+Enter 换行）      │
├──────────────────────────────────────────────────────┤
│  [build 默认 ▾]        [smoke-model ▾][思考 高 ▾][停止][发送] │
└──────────────────────────────────────────────────────┘
   状态栏： 完成。            上下文 44 / 1.0M ▬▬▬    累计 180 tokens
```

上下文用量（分母 + 进度条）在**状态栏**右侧。原先它在顶部工具条，三个选择器搬走后顶部只剩这一项，与其留一条只有一项的横栏，不如并入本来就在展示用量的状态栏。

## 思考等级

输入框下方、发送按钮左侧的**思考等级**下拉控制模型的推理强度。档位是**稳定 id**（`off` / `low` / `medium` / `high` / `max`），因为它要持久化到配置文件里，一旦发布就不能改名：

| 档位 | Anthropic（`thinking.budget_tokens`） | OpenAI 兼容（`reasoning_effort`） |
| --- | ---: | --- |
| `off` | 不传 thinking 字段 | 不传 `reasoning_effort` |
| `low` | 2048 | `low` |
| `medium` | 8192 | `medium` |
| `high` | 24576 | `high` |
| `max` | 49152 | `high` |

要点：

- 同一件事在两种协议里表达不同（Anthropic 用 token 预算，OpenAI 用枚举），Agent 循环按档位**同时填好两个字段**，provider 各取所需。`off` 的实现是**完全不传字段**，而不是传空值——部分兼容网关见到未知字段会直接 400。
- Anthropic 要求 `budget_tokens >= 1024` 且 `< max_tokens`，`clampReasoningBudget()` 会做一次收敛，保证发出的请求一定合法（`maxOutputTokens` 太小时会自动关闭思考而不是发出一个会被拒的请求）。
- **不支持思考的模型不显示这个下拉**，用户不会看到一个永远禁用的空控件。
- 每个模型上次用的档位会被记住（按 `providerId/modelId` 存），切换模型时自动恢复，不会静默重置。

## 模型上下文大小

Provider 自报的上下文窗口经常不准（第三方兼容服务尤其如此），而**窗口值错了会直接导致压缩阈值判断失误**。所以设置页里可以对每个模型覆盖：

- **上下文窗口**（`0` = 沿用内置默认，通常 128000，Claude 系列 200000）
- **最大输出**（`0` = 沿用默认）
- **思考档位**（该模型可用的档位列表，留空 = 用标准集合）与**默认档位**

覆盖的生效路径是**单点**的：`ProviderRegistry::setModelOverrides()` 会把覆盖应用到 `resolve()` 与 `allModels()` 返回的每一份 `ModelInfo` 上，因此状态栏的上下文用量分母、模型选择器、以及 Agent 循环里的压缩判断全都自动拿到有效值，不需要各处分别查询设置。

上下文用量在**会话一建立就显示**（此时已用为 0，但分母已知），改完设置立刻能看到反馈。

## 上下文压缩

会话越长，历史越占窗口。压缩分两级，触发点、代价与副作用都不同：

| 级别 | 何时触发 | 做什么 | 代价 |
| --- | --- | --- | --- |
| **microcompact** | 估算用量 ≥ 窗口 **70%** | 构造下发副本时，把**保护窗口之外**、超过 8000 字符的工具输出换成一行裁剪标记 | 零模型调用，确定性 |
| **full compact** | 估算用量 ≥ 窗口 **90%** | 调模型把早期历史摘要成一份"交接文档"，用合成消息替换那段历史 | 一次模型调用 |
| 手动 | 用户输入 `/compact` | 直接做 full compact（**不看阈值**） | 同上 |

几条刻意的设计：

- **检查点在每个模型步开始前**，不是回合结束。长回合内部会跑很多步，等到回合结束再收敛，中途就可能已经超窗被拒。
- **摘要请求是非阻塞的**：需要摘要时只发起请求，当前这一步仍用现有上下文发出去；摘要回来后才替换。这样压缩不会让用户干等。
- **两条阈值都显示在状态栏**（"上下文 3.4k / 64.0k · 自动压缩于 44.8k"），悬浮说明给出两个阈值的含义。用户不该靠猜"什么时候会被压"。
- microcompact **只改下发副本**。`ToolPart::output` 里的原文不动，工具卡片照旧显示完整输出——裁掉的是"再喂给模型的那一份"。
- full compact 的**裁剪点只落在 user 消息边界**。两种 provider 的线格式都要求 `tool_result` / `role=tool` 紧跟对应的 `tool_calls`，从中间切断会得到一个悬空的 `tool_use`，请求会被直接拒。
- 摘要消息是 **User 角色 + `modelOnly`**：`System` 角色不下发给 provider（两家 provider 都显式跳过），摘要就白写了；而 `modelOnly` 让它不出现在用户可见的对话流里。用户看到的是同一位置的**压缩分隔行**（`TimelinePart`）。
- **压缩不丢历史**。被替换掉的消息先写进 `archived_message` 表再删除，`SessionStore::archiveMessages()` 在同一个事务里做完两件事。归档表刻意不设外键，会话/消息删除时不跟着消失。
- 摘要与分隔行**随会话落盘**，重开应用后 `restoreContextSummary()` 会把摘要认回来；否则活动历史已经删掉、摘要又没存，就是永久丢失。
- 原文交给摘要模型的**只保留尾部**（近处更重要），提示词明确要求按"目标 / 已完成 / 关键决策 / 问题 / 当前状态 / 下一步"六段写，并写明"拿不准就写不确定，不要猜"。
- 估算**宁可高估**（约 3 字符/token，英文自然语言约 4）。高估的代价是压缩早一点发生；低估的代价是请求被 provider 拒绝。
- 估算口径包含**工具声明与系统提示词**。它们在小窗口里能占掉九成预算，不计的话"用量 3%"却已经超窗。
- 消息太少（默认少于 8 条）或没有完整的 user 轮可切时**不压缩**：摘要未必比原文便宜。
- 压缩失败**不算回合失败**。单独一条 `compactionNotice` 信号走到状态栏，不会显示成一次错误；本轮该发什么还是发什么，由 provider 决定是否超窗。

内建命令（输入框里以 `/` 开头，**不会发给模型**）：

| 命令 | 作用 |
| --- | --- |
| `/compact` | 立即压缩上下文 |
| `/help` | 列出可用命令 |

未知命令会在状态栏提示并**保留输入**，不会被当成提示词发出去——否则用户会以为自己敲的命令生效了。

## 界面语言与翻译

界面语言在设置页可切换（`zh-CN` / `en-US`），首装时**跟随系统 locale**。

技术路线是 Qt 的标准做法，没有自造轮子：

| 环节 | 做法 |
| --- | --- |
| 源文案 | 源码里写**英文**，用 `QCoreApplication::translate("<上下文>", "…")` 标记 |
| 抽取 | `lupdate` 扫源码 → `translations/lycode_zh_CN.ts` |
| 编译 | `lrelease` → `lycode_zh_CN.qm`，由 CMake 的 `qt_add_translations` **嵌进 `lycode_lib` 的资源**（`:/i18n/…`） |
| 装载 | 启动时（`MainWindow` 构造、`buildUi()` 之前）按设置装 `QTranslator` |

几个刻意的选择：

- **源文案是英文，而不是中文**。英文是界面开发的通用源语言，第三方贡献者不必先读中文才能改界面。代价是**中文界面依赖 `zh_CN.qm`**：漏译一处，那里就显示英文，而中文界面下"少了一条译文"是看不出来的（显示成英文才看得出来）。所以有一条测试专门断言"切成中文后按钮与菜单必须是中文"，避免翻译文件构建漏掉却无人发现。
- **上下文按"界面模块"划分**（`ui::MainWindow` / `ui::SettingsDialog` …），而不是按 C++ 类名自动生成。译者在 `.ts` 里能按界面分段阅读；同时这也避开了 `tr()` 的上下文取决于"声明它的类"这个陷阱——本项目大量文案写在匿名命名空间的自由函数与 lambda 里，那里根本没有 `tr()`。
- **语言装在建界面之前**。控件一旦构造就把文案写死了，之后再 `installTranslator` 只能等 `LanguageChange` 事件来重译。装晚了的表现是"第一屏是上一种语言，点一下才变"。
- **切换语言后弹窗询问是否立即重启**，而不是假装已经生效。Qt 的重译依赖 `LanguageChange` 事件，而本窗口的控件文案是构造期一次性写死的——当场只会得到一个中英混杂的界面。逐控件重译要把上百处赋值搬进 `retranslateUi()`，风险高于收益；重启一次是确定正确的（所有控件都用新语言重新构造）。选「稍后」时状态栏保留提示。
- **首装跟随系统 locale**，而不是写死一种语言。源码是英文，写死 `zh-CN` 会让英文用户一进来就面对中文界面；写死 `en-US` 则相反。`AppSettings::language` 为空即表示"用户还没选过"。

### 哪些文案**不**翻译

工具描述、参数说明、系统提示词是**发给模型的指令**，不是界面文案。翻译它们会改变模型行为，也拿不到任何本地化收益——它们保持源码里的字面量（英文）。

这条边界有机器守着：`scripts/check-translations.py` 校验 `.ts` 里不出现已知的模型文案。它查的是 `.ts` 而不是源码——`.ts` 是"哪些文案被标记为可翻译"的权威产物，只有真被 `translate()` 包住的字符串才会出现在里面。

**判定依据是"谁看得见"，不是"谁收到"**：

- **翻译**：所有会显示在界面上的文本。包括工具执行结果的文案（`ToolResult::failure(...)`、`launch.error`），因为它们会渲染在工具卡片里——中文用户看得到，就该是中文。这里容易被"它也会回灌给模型"带偏：界面语言在一次运行里是固定的，同一会话内这些文本不会来回变，因此不构成上下文不稳定。
- **不翻译**：发给模型的**指令**——系统提示词、工具与参数的 JSON Schema 说明。翻译它们会改变模型行为，也没有本地化收益。它们保持源码里的英文字面量（`QStringLiteral`）。
- **也不翻译**：解析模型输出用的固定前缀（如标题提取里的 `标题：`），那是协议的一部分。

这条边界由 `scripts/check-translations.py` 机器守着：它**自动从源码提取**所有 Schema 说明，断言它们不出现在 `.ts` 的 `<source>` 里。名单是提取出来的而不是硬编码的——硬编码会随"新增一个工具"而失效，而新工具的描述照样可能被人顺手包进 `translate()`。

### 怎么加一条新文案

1. 源码里写**英文**，用 `QCoreApplication::translate("<上下文>", "…")` 包起来
   （上下文取界面模块名，如 `ui::MainWindow`；不要用 `tr()`——本项目的文案大量写在
   匿名命名空间的自由函数与 lambda 里，那里没有 `tr()`）。
2. `python3 scripts/update-translations.py` 刷新 `.ts`，新文案会以
   `type="unfinished"` 出现。
3. 在 `translations/lycode_zh_CN.ts` 里填中文（用 Qt Linguist 打开，或直接编辑 XML）。
4. `python3 scripts/check-translations.py` 确认没有把"给模型的文案"标记成可翻译。
5. 重新构建：`lrelease` 会在构建时把 `.ts` 编成 `.qm` 并嵌进资源。

**`.ts` 是译文的唯一真相来源**。早先迁移阶段曾经用一份 `source-map.json`
（中文 ⇒ 英文）+ 纯文本 `zh_CN.txt` 作为作者入口，好处是几百条译文能在 diff 里逐条
review；代价是同一批译文存在于两处、而没有任何机制阻止它们漂移（直接用 Linguist 改了
`.ts`，那份 json 就悄悄过期）。迁移完成后这两份中间产物与仅供它们使用的脚本都已删除，
现在只有一个可改的地方。

⚠ `lupdate` 在部分 Linux 发行版上是 `qtchooser` 的符号链接，未配置 Qt 环境时会报
`could not find a Qt installation of ''`。`update-translations.py` 会**实测**候选二进制
是否真能运行（跑一次 `-version`），而不是只看路径存在——后者永远会选中这个壳。

权限弹窗里的「始终允许」会固化一条规则（按工具 + 路径/命令前缀匹配），后续同类调用不再打扰。规则只存在内存里，切换会话即失效。
